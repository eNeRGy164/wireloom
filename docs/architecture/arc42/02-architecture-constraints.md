# 2. Architecture constraints

This chapter records the non-negotiable product boundaries and mandatory
project policies that every design must satisfy. Each entry identifies its
scope, consequence, and authority. The [solution strategy](04-solution-strategy.md)
and [decision records](09-architectural-decisions.md) describe the chosen
architecture within these boundaries.

## 2.1 Product and execution boundaries

These technical and integration constraints apply to the consumer build,
browser preview, or live DDS execution as stated.

| Constraint                                                                           | Rationale                                                        | Design impact                                                                                                               | Source                                                                                                                                                                                                        |
| :----------------------------------------------------------------------------------- | :--------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Consumer applications require .NET 8 or later and C# 12 or later                     | Preserve the documented consumer baseline                        | Generated code must compile and use APIs available on the minimum supported baseline                                        | [Consumer requirements](../../../README.md#support-and-compatibility)                                                                                                                                         |
| The analyzer must load in the .NET 8 SDK's Roslyn 4.8.0 host                         | Consumers must not need the repository's newer SDK               | Analyzer dependencies and emitted source are checked with the minimum compiler host                                         | [Host compatibility decision](09-architectural-decisions.md#91-decision-timeline), [package checks](../../guides/support-and-compatibility.md#continuous-lts-verification)                                    |
| Consumer generation requires a resolved `Rti.ConnextDds` reference of at least 7.3.1 | Generated support must match the application's RTI runtime       | Missing or older references fail generation; this assembly requirement does not apply to direct compiler or browser callers | [RTI version policy](../../guides/support-and-compatibility.md#rti-version-qualification)                                                                                                                     |
| Consumer builds must not invoke Java, native generation tools, or `rtiddsgen`        | Generation belongs to the normal .NET restore and build workflow | Generation must work without provisioning an external generator toolchain                                                   | [Requirements and non-goals](01-introduction-and-goals.md#11-requirements-overview)                                                                                                                           |
| Playground IDL stays in the browser; the preview does not perform DDS communication  | The Playground is a local demo and evaluation tool               | No service receives workspace source, and preview results do not establish runtime or wire compatibility                    | [Playground purpose](01-introduction-and-goals.md), [source boundary](../dependency-intake/playground-frontend.md)                                                                                            |
| Live DDS exchanges require the selected RTI runtime and applicable license           | Wireloom does not replace RTI runtime provisioning or licensing  | Licensed peer execution is separate from license-free generation and report verification                                    | [Support boundary](../../guides/support-and-compatibility.md#support-boundary), [wire prerequisites](../../../tests/Wireloom.Dds.Generator.WireCompatibility/README.md#container-variants-and-local-wire-run) |

## 2.2 Evidence and provenance policies

These organizational requirements govern compatibility claims and retained
third-party material.

| Constraint                                                                                                  | Rationale                                                                                | Design impact                                                                                                                          | Source                                                                                                                                                                        |
| :---------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Compatibility claims require retained evidence for named inputs and exact RTI releases                      | Implemented generation, API behavior, and DDS interoperability establish different facts | Keep their evidence separate; exact 7.3.1 and 7.7.0 are the qualification targets, and profile mapping does not qualify other releases | [Qualification policy](../../guides/support-and-compatibility.md#rti-version-qualification), [evidence vocabulary](08-crosscutting-concepts.md#85-compatibility-and-evidence) |
| RTI oracle captures retain input/tool provenance and original notices; corpus case identities remain stable | Results must remain attributable and traceable                                           | Preserve versioned captures, notices, manifest identities, and existing case references                                                | [Corpus rules](../../corpus/README.md), [LTS capture profiles](../../corpus/LTS-PROFILES.md)                                                                                  |
| Evidence artifacts must exclude license files and secret values                                             | Reproducible reports must not expose execution credentials                               | Retain source, toolchain, image, and result provenance while keeping licenses outside the evidence bundle                              | [Wire evidence rules](../../../tests/Wireloom.Dds.Generator.WireCompatibility/README.md#container-variants-and-local-wire-run)                                                |

## 2.3 Mandatory repository policies

These project-owned rules apply to repository changes. Consumer applications
retain the separate compatibility baseline in section 2.1.

| Constraint                                                                                                  | Rationale                                                    | Design impact                                                                                                                                 | Source                                                                                                                                                                                                                                      |
| :---------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Repository projects default to `net10.0` and use the SDK policy in `global.json`                            | Maintain a consistent development and quality-tool baseline  | Honor `latestFeature` roll-forward and disabled prereleases; documented analyzer/compiler targets and consumer checks retain their exceptions | [Repository instructions](../../../AGENTS.md), [build defaults](../../../Directory.Build.props), [SDK policy](../../../global.json)                                                                                                         |
| Use central .NET versions, locked restores, audit, approved NuGet sources/signatures, and pinned CI actions | Keep dependency changes reproducible and reviewable          | Restore and dependency updates must satisfy repository controls                                                                               | [Package versions](../../../Directory.Packages.props), [build defaults](../../../Directory.Build.props), [NuGet policy](../../../NuGet.Config), [publication controls](07-deployment-view.md#713-package-production-and-distribution)       |
| Tests run through Microsoft.Testing.Platform                                                                | Keep test execution consistent with the configured runner    | Test commands and filters must use the documented runner syntax                                                                               | [SDK runner configuration](../../../global.json), [repository instructions](../../../AGENTS.md)                                                                                                                                             |
| Generator-quality changes complete the documented build, test, coverage, Qodana, CI, and Coveralls checks   | Compatibility and quality claims require reviewable evidence | Local passing tests alone do not complete the required verification                                                                           | [Quality workflow](../../../.agents/instructions/pr-feedback-and-quality-workflow.md#verify-the-complete-change), [quality evidence](../../../CONTRIBUTING.md#quality-evidence)                                                             |
| Architecture docs use US English Markdown and PlantUML sources under the chapter's image directory          | Keep architecture changes consistent and reviewable          | Maintain diagrams as `.puml` sources under `images/<chapter>/`                                                                                | [Repository instructions](../../../AGENTS.md)                                                                                                                                                                                               |
